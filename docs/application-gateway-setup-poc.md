# Adding Application Gateway in Front of the App Container App (POC / Simple Version)

Simplified high-level steps for this project's POC — no WAF, no custom domain, no real certificate. Just enough to expose the `app` container app publicly through Application Gateway while keeping the CAE internal.

## 1. Keep the CAE internal

- `container-apps-environment.bicep` already exposes a `publicNetworkAccess` param (default `'Disabled'`) that sets `internal: true` on the AVM `managed-environment` module — no change needed there, just confirm the `app` CAE's module call in `main.bicep` doesn't override it to `'Enabled'`.
- The module already outputs `staticIp` — no new output needed, just wire it through `main.bicep` to the new `application-gateway.bicep` module and to step 3's DNS module.
- You still need the CAE's **default domain** (e.g. `<env>.<region>.azurecontainerapps.io`) for the DNS zone name in step 3. The AVM `managed-environment` module doesn't currently output this, so add `output defaultDomain string = managedEnvironment.outputs.defaultDomain` if the pinned AVM version exposes it (check `br/public:avm/res/app/managed-environment` docs for the pinned version) — safer than reconstructing the domain string yourself, since it's generated by Azure at CAE creation time.

## 2. Add a gateway subnet

- In `vnet.bicep`, add a subnet (e.g. `agw`), `/24`, no delegation.

## 3. Private DNS zone for the CAE default domain

Added directly inside `container-apps-environment.bicep` (no separate module file needed), following the same `br/public:avm/res/network/private-dns-zone` pattern already used in `key-vault.bicep`:

- New `virtualNetworkName` param, wired from `main.bicep` as `vnet.outputs.name`.
- A conditional (`publicNetworkAccess == 'Disabled'`) `private-dns-zone` module: zone `name` is the CAE's own `defaultDomain` output (not a `privatelink.*` name, since CAE private DNS uses the domain itself), linked to the VNet with `registrationEnabled: false`.
- Wildcard `*` and root `@` A records via the module's `a` array, both pointing at `managedEnvironment.outputs.staticIp`.

## 4. Provision Application Gateway (Standard_v2, no WAF)

- Use AVM module `br/public:avm/res/network/application-gateway`.
- `sku: 'Standard_v2'` (skip `firewallPolicyResourceId` entirely — no WAF for POC).
- Disable autoscaling and pin fixed capacity to one instance (`autoscaleMinCapacity: -1`, `autoscaleMaxCapacity: -1`, `capacity: 1`).
- `gatewayIPConfigurations` → the `agw` subnet.
- `frontendIPConfigurations` → a new public IP (Standard SKU).
- `backendAddressPools` → the `app` container app's FQDN.
- `backendHttpSettingsCollection` → port 443, protocol `Https`, `pickHostNameFromBackendAddress: true`.
- `requestRoutingRules` → `ruleType: 'Basic'`, tie listener + pool + settings together.

## 5. Certificate — simplest option: self-signed (reference sample)

- Reference implementation: [`Azure-Samples/apptemplate-wordpress-on-aca`](https://github.com/Azure-Samples/apptemplate-wordpress-on-aca), specifically `infra/applicationGateway.bicep` and `infra/cert/`. This azd sample pairs Application Gateway with a container backend using a self-signed cert stored in Key Vault — closest known working reference for this exact pattern.
- Pattern to copy:
  - Generate a self-signed cert locally (e.g. `openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes`, then export to PFX), or reuse a committed test cert like the sample does.
  - Store the PFX as a certificate/secret in the existing Key Vault (reuse the one already in this repo).
  - Give the Application Gateway a **user-assigned managed identity**, and grant it `Key Vault Secrets User` (or an access policy, per the sample) so it can pull the cert at runtime.
  - Reference the cert in `sslCertificates` via `keyVaultSecretId` (not inline base64 data) — matches the sample and avoids storing cert bytes directly in Bicep params.
- Listener protocol `Https` on port 443 using this cert.
- Browsers will show a "not secure" / cert warning — expected and fine for POC, just click through.

## 6. Skip custom domain

- Access the app via the Application Gateway's public IP directly (or its Azure-assigned public IP DNS label), not a custom domain.
- No DNS changes needed outside the internal Private DNS zone from step 3.

## 7. Wire into `main.bicep`

- Add `agw` subnet output from `vnet.bicep`.
- Add the new `application-gateway.bicep` module call, depending on `vnet` and the `app` container app's FQDN.
- Output the gateway's public IP for quick access.

## 8. Validate

- `azd provision`, then browse to the gateway's public IP over HTTPS and accept the self-signed cert warning.
- Confirm Entra sign-in redirect still completes (host header should still match the app's expected redirect URI — you may need to register the gateway's public IP/hostname as a redirect URI in the app registration for POC purposes).

## What's skipped vs. the prod version

- No WAF / firewall policy.
- No real public certificate — self-signed only.
- No custom domain / public DNS — access by IP.
- No `X-Forwarded-Host` rewrite rule (only add if Entra redirect breaks due to host header mismatch).

See [application-gateway-setup.md](./application-gateway-setup.md) for the full production version with WAF, custom domain, and a proper certificate.
